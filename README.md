# A/B Test Analytics with SQL

一个面向数据科学岗位求职的 SQLite 实验分析小项目：从新用户引导 A/B 实验的原始事件出发，完成事件去重、ITT 指标构建、SRM 检查、双比例 z 检验、置信区间、护栏指标和探索性分层分析。

> **数据声明：本项目所有数据均为固定随机种子的合成数据，不代表真实用户、真实游戏或真实业务结论。** 项目重点是展示可复现的 SQL 与实验分析方法，而不是包装虚构的业务成果。

## 项目亮点

- **SQL 核心能力：**CTE、窗口函数去重、条件聚合、左连接保留 ITT 分母、表约束与索引。
- **实验分析能力：**用户级随机分流、SRM、明确时间窗、绝对/相对提升、95% CI、双比例 z 检验。
- **数据科学表达：**区分确认性主指标、探索性次要指标、护栏指标和设备分层，避免把“不显著”误写成“没有风险”。
- **工程可复现：**零第三方 Python 依赖，一条命令重建数据库并更新结果，单元测试独立交叉校验，CI 检查结果一致性。

## 1. 业务问题与实验假设

某产品希望评估“简化新用户引导流程”是否能让更多新用户完成教程。实验将新用户按用户级 1:1 随机分为：

- `control`：原有引导流程。
- `treatment`：简化后的引导流程。

**原假设 H0：**两组用户的 24 小时教程完成率相同。  
**备择假设 H1：**两组用户的 24 小时教程完成率不同（双侧检验）。

| 设计项 | 口径 |
|---|---|
| 随机化单元 | 用户 |
| 分析原则 | Intention-to-Treat（ITT），所有已分流用户进入对应组分母 |
| 主指标 | 24 小时教程完成率，alpha=0.05，双侧确认性检验 |
| 次要指标 | D1 留存率，只作探索性解读 |
| 护栏指标 | 24 小时崩溃用户率，只报告估计与不确定性 |
| 分层变量 | 分流前已知的设备类型 Android/iOS，只作探索性分析 |
| 模拟分流期 | 2026-09-01 起 28 天；每名用户均有完整 48 小时合成观察窗口 |

## 2. 数据模型

`schema.sql` 只保存原始表、约束和索引，不把分析结论写入数据层。

### `assignments`

| 字段 | 含义 |
|---|---|
| `user_id` | 用户 ID，主键；保证一个用户只有一个分组 |
| `variant` | `control` 或 `treatment` |
| `assigned_at` | 随机分流时间，UTC Unix 秒，是所有指标窗口的锚点 |
| `device_type` | 分流前已知的 `android` / `ios` |

### `events`

| 字段 | 含义 |
|---|---|
| `ingest_id` | 原始摄入顺序，主键；用于确定性去重 |
| `event_id` | 客户端事件 ID；原始表允许重复，以模拟日志重传 |
| `user_id` | 外键，关联 `assignments` |
| `event_name` | `tutorial_complete` / `app_open` / `crash` |
| `occurred_at` | 事件发生时间，UTC Unix 秒 |

同一个 `event_id` 若对应不同用户、事件名或时间，会被质量检查标记为冲突，而不是静默去重。

## 3. 指标口径

所有窗口均为**左闭右开**，避免边界重复计数。

| 指标 | SQL 口径 |
|---|---|
| 24 小时教程完成率 | 首次分流后的完成事件位于 `[assigned_at, assigned_at + 86400)`；分母为全部分流用户 |
| D1 留存率 | 至少一次 `app_open` 位于 `[assigned_at + 86400, assigned_at + 172800)` |
| 24 小时崩溃率 | 至少一次去重崩溃事件位于 `[assigned_at, assigned_at + 86400)`，按用户率计算 |

无事件用户通过左连接保留在 ITT 分母中；重复事件在指标计算前统一去重。项目不比较“仅在教程完成者中的完成耗时”，避免按暴露后变量筛选用户造成选择偏差。

## 5. SQL 分析路径

| 文件 | 作用 |
|---|---|
| `sql/01_analysis_base.sql` | `ROW_NUMBER()` 按事件 ID 去重，构建一行一用户的 ITT 视图 |
| `sql/02_data_quality.sql` | 检查分组、孤立事件、冲突事件 ID、分析视图粒度，并报告移除的重复行 |
| `sql/03_srm.sql` | 对 1:1 分流执行卡方拟合优度检查，`p < 0.01` 时中止实验结论 |
| `sql/04_primary_metric.sql` | 计算主指标、绝对/相对提升、95% CI、双比例 z 与双侧 p 值 |
| `sql/05_secondary_guardrail.sql` | 计算 D1 留存与崩溃护栏；护栏不输出“安全/不安全”的显著性结论 |
| `sql/06_device_subgroup.sql` | 输出设备分层效应估计与名义 CI，不作确认性 subgroup 结论 |

主指标的**置信区间**使用非合并标准误，描述差值的估计不确定性；**z 检验**使用原假设下的合并比例和标准误。两者用途不同，因此公式并非误写。

SRM 使用自由度 1 的卡方生存函数，双侧正态检验使用：

```text
p = erfc(abs(z) / sqrt(2))
```

## 6. 本地复现

要求 Python 3.11+，只使用标准库；无需安装 SQLite 服务或任何 pip 包。

```bash
python run_analysis.py
python -m unittest discover -s tests -v
```

第一条命令会从零重建 `build/ab_experiment.sqlite3`，执行全部分析 SQL，并更新：

- `results/summary.md`：质量检查、SRM、全部指标与结果解读。
- `results/metrics.csv`：便于复核的长表指标结果。
- 本 README 的“实际运行结果”区域。

当前 SQLite 环境不一定编译了数学扩展，因此 `run_analysis.py` 通过 Python 标准库 `math.sqrt`、`math.erfc` 注册确定性 SQLite 函数。业务聚合和统计公式仍在 SQL 文件中；统计查询应通过运行脚本执行，而不是直接在未注册函数的裸 SQLite CLI 中运行。

如只需生成原始数据库：

```bash
python generate_data.py
```

## 7. 合成数据参数与设计依据

所有参数集中在 `generate_data.py` 的 `ExperimentConfig`，随机种子只用于复现，不根据显著性调整。

| 参数 | 数值 | 设计依据 |
|---|---:|---|
| 总用户数 | 6000 | 预期约 3000 人/组，高于主效应样本量需求，同时保持项目轻量 |
| 随机种子 | 20261115 | 保证生成与结果可复现 |
| 分流概率 | 0.5 / 0.5 | 用户级独立 Bernoulli 分流，使 SRM 检查有实际意义 |
| 对照/实验完成率参数 | 0.42 / 0.48 | 模拟 6 个百分点的预设绝对差，不等同于实际观测提升 |
| 对照/实验 D1 留存参数 | 0.30 / 0.33 | 演示次要指标及多重比较限制 |
| 对照/实验崩溃率参数 | 0.020 / 0.021 | 演示低发生率护栏估计的不确定性 |
| Android / iOS 比例 | 0.60 / 0.40 | 保证每层都有足够演示样本 |
| 原始事件重复比例 | 0.02 | 验证去重逻辑确实处理重复摄入 |

按双侧 alpha=0.05、80% power 的常规两比例正态近似，检出 0.42 到 0.48 的差异约需 **1080 人/组**。该计算是模拟实验的设计依据，不是运行后的功效声明。

## 8. 统计边界

- 只有主指标是预设确认性检验；D1 与设备分层不作多重比较校正后的确认性声明。
- 崩溃护栏未预设非劣效界值，不能用 `p > 0.05` 或“不显著”证明没有安全风险。
- 大样本双比例 z 检验依赖正态近似；样本很小或事件极稀少时应重新评估方法。
- 设备分层只描述各层效应估计，不等同于正式的 treatment-by-device 交互检验。
- 合成数据用于方法演示，不能外推为真实产品收益。

## 9. 面试讲解提示

1. **为什么使用 ITT？** 避免只分析活跃或已曝光用户而破坏随机化，保留原始分组的比较基础。
2. **为什么先查 SRM？** 分流实现若破坏预期比例，后续显著性结果可能反映实验执行问题，而不是真实处理效应。
3. **为什么先去重再定义用户指标？** 日志重传会放大事件计数；按 `event_id` 去重可保证同一行为只贡献一次。
4. **为什么同时报告绝对提升、相对提升和 CI？** 绝对提升对应业务规模，相对提升便于比较，CI 展示估计的不确定性。
5. **为什么不把护栏“不显著”写成“安全”？** 未拒绝相等假设不等于证明等效或非劣效，需要预设界值和相应设计。
